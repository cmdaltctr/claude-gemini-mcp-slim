Title: 002.2-Refactoring AI API Logic to a Decoupled Modular Architecture
Date: 2025-08-02
Decision Maker: Dr Muhammad Aizat Hawari
Status: Accepted

## Context

Following the architectural problems identified in [ADR 002.1](./002.1-Architectural-Problems-and-Refactoring-Initiative.md), this document details the implementation approach for refactoring AI API interaction logic to follow a decoupled, modular architecture. The tight coupling between the MCP communication layer and AI backend interaction logic needed to be resolved to improve maintainability, testability, and scalability.

## Decision

We have decided to implement a decoupled modular architecture that clearly separates concerns between:

1. **The Communicator** (`gemini_mcp_server.py`) - Handles MCP requests and responses, orchestrates workflows
2. **The AI Specialist** (`gemini_helper.py`) - Manages all interactions with the Gemini backend (API or CLI)
3. **Specialized Processing Engines** (`helpers/` directory) - Pre-processing and post-processing utilities

This architecture follows the principle that each module has one clear responsibility, ensuring:
- MCP communication logic remains separate from AI interaction logic
- AI backend interactions are isolated and easily testable
- Helper utilities provide specialized processing capabilities

## Consequences

### Positive Consequences
- **Clear Separation of Concerns**: Each module has a single, well-defined responsibility
- **Improved Testability**: Individual components can be tested in isolation
- **Enhanced Maintainability**: Changes to AI logic don't affect MCP communication and vice versa
- **Better Scalability**: New AI backends or processing capabilities can be added without affecting existing modules
- **Reduced Coupling**: Dependencies between components are minimized and well-defined

### Challenges
- **Initial Refactoring Effort**: Existing tightly coupled code needs to be carefully separated
- **Interface Definition**: Clear interfaces between modules need to be established and maintained
- **Configuration Management**: Centralized configuration system must be used consistently across all modules

## Implementation Guidelines

### Module Responsibilities

**gemini_mcp_server.py (The Communicator)**:
- Handle MCP protocol requests and responses
- Orchestrate workflows by calling appropriate modules
- Must NOT contain direct AI API call logic
- Focus solely on MCP communication and workflow management

**gemini_helper.py (The AI Specialist)**:
- Manage all interactions with Gemini backend (API or CLI)
- Handle API/CLI fallback logic
- Construct prompts and parse AI responses
- Must NOT contain MCP communication logic

**helpers/ directory (Specialized Processing Engines)**:
- `tools/codebase_analyzer/`: Pre-processing engines for static analysis
- `tools/analyze_code/`: Single file analysis utilities
- `markdown_utils.py`: Post-processing formatter for consistent output
- `security.py`: Input sanitization and path validation utilities
- `execution_orchestrator.py`: AI execution management

### Configuration Management
- All configuration values must be accessed through `config.py` accessor functions
- No direct use of `os.getenv()` or hardcoded values outside of `config.py`
- Centralized, thread-safe configuration management

### Future Evolution
This architecture supports the planned evolution toward the Agentic Collaboration Protocol (ACP), where structured JSON objects (like `AgenticCodePatch`) will be exchanged between components, enabling more sophisticated AI-human collaboration workflows.

## Alignment with Project Rules

This decision directly implements the architectural integrity principles defined in the project's AI Agent Golden Rules:

1. **Core Philosophy**: Acts as an intelligent orchestrator, not a simple bridge
2. **Decoupled Module Pattern**: Strict adherence to the separation between Communicator, AI Specialist, and Processing Engines
3. **Configuration Management**: Centralized configuration system for all settings
4. **Modularity**: Clear responsibility separation enabling maintainable and testable code

This architecture decision ensures the project remains scalable, maintainable, and aligned with modern software engineering best practices while supporting the evolution toward more sophisticated AI-driven development workflows.

## Testing Implications

The architectural refactoring from monolithic to decoupled modular architecture has significant testing implications that require comprehensive coverage across multiple dimensions:

### New Unit Tests Required

**gemini_helper.py (The AI Specialist)**:
- `execute_gemini_api()` - Test API calls with various inputs, error conditions, and API key scenarios
- `execute_gemini_cli_streaming()` - Test CLI fallback with various inputs and timeout scenarios
- `execute_gemini_smart()` - Test orchestration logic, including API-to-CLI fallback mechanisms
- API key discovery functions - Test each discovery method and fallback chain

**helpers/security.py (Security Module)**:
- `sanitize_for_prompt()` - Tests for various input patterns, including potential injection attacks
- `validate_path_security()` - Tests for various path patterns, including potential traversal attacks
- Penetration tests with known attack patterns and fuzzing tests with random inputs

**config.py (Configuration Management)**:
- Configuration loading from different sources (explicit args > env vars > config.json > defaults)
- Typed accessors and nickname support validation
- Thread-safe caching mechanisms

### Integration Tests Strategy

**Cross-Module Integration**:
- End-to-end tests with mocked API responses for complete workflows
- Tests for CLI fallback when API is unavailable
- Configuration integration across all modules with override validation
- Large input/output handling across the decoupled architecture

**MCP Server Integration**:
- Updated request handlers using `execute_gemini_smart()` orchestration
- Proper input validation and sanitization through security module
- Error handling and response formatting across module boundaries

### Security Test Requirements

**Security-Critical Functions (100% Coverage Goal)**:
- Comprehensive testing of sensitive information handling (API keys)
- Error handling and information redaction validation
- Path traversal and prompt injection attack prevention
- Input sanitization across all entry points

### Coverage Goals and Mocking Strategies

**Coverage Targets**:
- \>90% code coverage for all new and modified code
- 100% coverage for security-critical functions
- Both happy path and error path testing inclusion

**Mocking Strategy**:
- Mock external API calls to Google Generative AI
- Mock subprocess calls for CLI testing scenarios
- Dependency injection implementation to facilitate comprehensive testing
- Comprehensive test fixtures for valid/invalid inputs and edge cases

### CI Pipeline Enhancements

**Automated Quality Gates**:
- Unit tests for isolated module functionality
- Integration tests for cross-module interactions
- End-to-end tests for complete user workflows
- Security tests for vulnerability prevention
- Performance tests for orchestration overhead
- Configuration matrix tests for different deployment scenarios
